# 花生1000词汇卡内容重建设计

## 目标

把已经判定为不合格的 974 词预览重新制作成真正服务于言语理解做题的学习材料。数量和字段不得替代语义质量；未通过逐项审查的内容不进入正式预览。

## 当前版本为何作废

- 应用题把核心辨析槽直接放进题干，974 题只有 5 种骨架，属于定义问句。
- 辨析卡缺少逐词完整词义和“怎么选”，一眼辨析只是逐词核心列表。
- 一部分核心辨析由词义机械切分，出现标点残片、括号断裂和虚词槽。
- 维度由同一构建程序生成并自签；大量维度只是拆开核心辨析重说，77 个不足结论使用同一理由骨架。
- GitHub 只验证程序和自报统计，没有验证本地私人卡片的真实语义内容。

## 工件边界

1. `semantic_review_v2.json`：逐词保存准确词义、2—4 槽关键词核心、可观察线索、误用边界、证据位置和人工审查结论。
2. `comparison_review_v2.json`：只保存真实近义组。每组包含完整成员、逐词档案、一眼辨析边、至少一条“何时选谁”的规则；候选分组不得直接成为正式分组。
3. `dimension_review_v2.json`：与卡片渲染分离。每个正式近义组必须明确批准真实新增维度或说明不足；维度不得复述任何成员核心。
4. `application_authoring_v2.json`：每词一条自然、具体、有主体和事件的语境；答案词及核心槽不得原样出现在题干。每个干扰项都绑定具体排除条件。
5. `preview_acceptance_v2.json`：绑定上述四个工件哈希、最终三类预览哈希和逐项失败清单。

## 内容规则

### 基本词义

- 核心辨析必须是 2—4 个语义完整的关键词槽，不能含断裂括号、单独虚词或词典原句的机械残片。
- 词义回答“是什么”；核心回答“做题锁什么”；题干线索回答“材料里能圈什么”，三者不得互相改写充数。
- 未完成审查的词标为 `pending`，不允许用自动结果冒充 `ready`。

### 近义辨析

- 组身份先于卡片：必须先确认成员确为同一选择问题中的竞争词。
- 每个成员只解释一次完整词义与核心辨析。
- 一眼辨析必须是两个具体词之间的最短对立，不能只是并列逐词核心。
- “怎么选”必须用题干条件指向具体词，并覆盖组内全部成员。
- 多维判断只有在两个以上新增判断轴成立时显示；把核心槽拆成对象轴、结果轴仍属于重复。

### 场景应用

- 题干必须包含真实主体、事件、限制条件和结果，不能出现“题干先写到”“明确出现某落点”等元话语。
- 不得直接引用答案词、完整核心槽或词义定义。
- 同一抽象骨架不得主导整批；场景应覆盖公共治理、科技、文化、经济、个人行为等真实语域。
- 最佳答案必须唯一；每个干扰项说明缺失条件或冲突条件。

## 审查与 GitHub 边界

- 本地私人内容由哈希绑定的逐项审查工件验收；GitHub 对程序、合同、对抗测试和公开统计执行门禁。
- GitHub 绿灯只代表代码门禁通过，不得表述成私人卡片语义已经通过。
- 当前任务只生成预览；全库快照不完整时继续阻止墨墨写入。

## 验收

- 旧预览质量状态为 `rejected`。
- 974 个词全部有明确 `approved` 或 `pending` 结论；只有 `approved` 进入成品。
- 任何定义问句、残缺核心、比较卡缺层、伪维度或多解应用题都会使生成器非零退出。
- 最终报告分别给出批准数、待审数、正式近义组数、应用题数及所有阻断原因，不再以“目标必须凑满 974”覆盖语义问题。
