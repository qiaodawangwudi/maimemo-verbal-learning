# 言语墨墨制卡 Skill 与受保护发布系统设计

日期：2026-08-17

状态：待用户审阅

## 1. 目标

把已经验证过的言语理解词汇制卡流程做成可长期复用的 Skill，同时把容易被代理绕过的关键约束下沉为机器门禁。

系统的最高目标不是把字段填满，而是让最终卡片帮助学习者：

1. 准确理解词义；
2. 抓住词语真正特殊的语义落点；
3. 从有用维度区分近义词；
4. 在新的言语理解题中根据语境准确选择。

只有内容判断、动作计划、用户授权、线上写入和完整回读全部通过，任务才算完成。

## 2. 已确认的核心原则

采用“仓库维护唯一主版本，Skill 负责流程，发布引擎负责硬门禁”的方案。

墨墨令牌只保存于 GitHub 的受保护环境。Codex 本地进程、个人 Skill、工作区文件、提交记录、日志和卡片内容均不得获得或保存令牌。GitHub 最终授权没有成功时，任何由 Codex 控制的本地程序都没有调用墨墨写接口的凭据。

## 3. 不解决的事项

- 不假定开放 API 支持删除；未验证的删除接口不得使用。
- 不承诺机器规则能够独立证明语义真理。机器门禁负责确定性事实，完整语义审查负责学习价值。
- 不把老师口语直接视为合格应用题。
- 不把旧脚本、旧卡片或旧模型输出视为正确来源。
- 不允许写入程序在运行时生成、改写或补齐内容。
- 不以抽样检查代替全量审查。

## 4. 历史失败必须形成的系统约束

| 历史失败 | 根因 | 新系统约束 |
|---|---|---|
| 已有同标题卡被直接标为不变 | 标题查重代替语义对账 | 按规范词面、义项、语义、新证据和近义边生成动作 |
| 已有辨析卡只复用 root ID | 没有重算整个近义组 | 组成员或证据变化时，整组与所有关联基础卡同步重算 |
| 自动课程大组过宽 | 课程位置被误当成语义关系 | 课程分组只产生候选边；每条近义边必须审查 |
| 词义、特别之处和判断维度重复 | 字段存在被误当成信息有效 | 每个字段必须提供新的学习信息；无独立价值的字段省略 |
| 最小差别复制定义 | 只检查非空和文本格式 | 差别必须给出共同基础、判断轴及双方不同落点 |
| 后续批次明显简化 | 生成任务被当作批量填表 | 每条语义记录和每张最终卡必须有独立审查结果 |
| 应用卡曾被遗漏 | 应用价值未进入总账 | 每个词义和辨析组必须有 create 或 not_needed 决定 |
| 应用题照搬课堂口语 | 证据语句和训练语句未分开 | 题干只能重新创作或深度改编，并记录语义依据 |
| 先写入再发现问题 | 写入器与生成器耦合 | 写入器只消费不可变发布包；发布包未批准时无令牌 |
| 中断形成部分写入 | 没有幂等和恢复协议 | 同名同内容跳过；同名不同内容阻断；按线上状态恢复 |
| 程序结束被报告为完成 | 没有分层完成定义 | 提取、语义、计划、发布、回读五层分别给出证据 |
| 用户改章节后沿用旧计划 | 路由未进入授权对象 | 卡组、章节、类型映射和逐章数量全部进入发布哈希 |
| GitHub 最终授权失败但本地仍能写 | 本地持有令牌，门禁可旁路 | 令牌只在受保护 GitHub 环境中释放 |

## 5. 信任边界

### 5.1 Codex 可以做

- 读取用户提供的课程材料和旧库快照；
- 生成候选词、语义档案、近义关系和应用题；
- 运行全量审查并反复修订本地成果；
- 创建内容 PR；
- 在所有检查通过后发起受保护发布工作流；
- 读取发布状态和最终回读报告。

### 5.2 Codex 不可以做

- 读取墨墨令牌；
- 在本地调用墨墨写接口；
- 修改发布包后继续使用旧授权；
- 在 GitHub 检查失败时走备用写入路径；
- 把旧发布包、聊天中的口头批准或本地 JSON 当成 GitHub 最终授权；
- 在写入阶段临时修卡。

### 5.3 用户保留的权限

- 决定材料是否可以进入公开仓库；
- 审阅最终发布摘要；
- 对精确发布哈希执行一次最终授权；
- 在紧急情况下撤销 GitHub 环境授权或轮换墨墨令牌；
- 手动管理墨墨章节和无法通过开放 API 删除的旧卡。

## 6. 代码和 Skill 的唯一来源

仓库新增：

```text
skills/verbal-maimemo-cards/
├── SKILL.md
├── agents/openai.yaml
├── references/
│   ├── artifact-contracts.md
│   ├── learning-quality-rubric.md
│   ├── release-state-machine.md
│   └── source-and-privacy-policy.md
└── scripts/
    └── install_or_verify.py
```

仓库中的 `skills/verbal-maimemo-cards` 是唯一主版本。本机 `C:\Users\admin\.codex\skills\verbal-maimemo-cards` 是安装副本，不允许独立演进。

安装脚本执行以下操作：

1. 校验仓库 Skill 文件哈希；
2. 拒绝覆盖存在未记录修改的本机 Skill；
3. 原子替换安装目录；
4. 回读文件并验证安装哈希；
5. 输出仓库提交号和 Skill 版本。

制卡和发布的确定性逻辑继续由 `maimemo_learning_rebuild` 包实现，避免在 Skill 目录复制第二套业务代码。

## 7. 工件模型

每次任务生成独立的 `release_id`，所有中间工件进入该发布目录，不复用不明来源的历史文件。

### 7.1 来源清单

`source_inventory.json` 包含：

- 每个源文件的相对标识、文件哈希和来源类型；
- 每个段落或时间段的稳定定位；
- 候选词、例句词、选项词和老师小结词的分类状态；
- ASR 原词面、规范词面和纠错理由；
- 排除候选及其理由；
- `public_ok` 或 `local_only` 数据分类。

没有完成逐段分类和覆盖率复核时，后续状态不得进入 `semantic_reviewed`。

### 7.2 语义主档案

`semantic_registry.json` 以 `规范词面 + sense_id` 为稳定键，记录：

- 准确词义；
- 特别之处；
- 做题识别点；
- 有区分作用的判断维度；
- 近义边；
- 易错边界；
- 老师证据或通用补充来源；
- 新旧证据对账决定；
- 生成审查与独立审查结论；
- `ready / pending / conflict / retired` 状态。

老师证据和通用补充不得混写。任何 `pending` 或 `conflict` 都阻断整批发布，但不允许用无证据内容将其机械改为 `ready`。

### 7.3 近义组档案

`comparison_groups.json` 对每个成员和每条边记录：

- 共同语义基础；
- 比较轴；
- 两侧不同落点；
- 为什么适合共同学习；
- 来源证据；
- 与其他组的重叠类型和保留理由。

结构门禁要求成员唯一、顺序稳定、2至6个成员、最小差别图连通。语义审查额外确认该组确实有共同基础，不能仅因图连通而通过。

### 7.4 应用价值档案

`application_review.json` 必须覆盖每个 ready 词义和每个 ready 辨析组。每个对象只能有一个决定：

- `create`：说明独立训练价值和目标差别；
- `not_needed`：说明为什么基础卡或现有应用卡已经足够。

应用卡生成者只负责题目草案。独立盲解审查只看题干和选项，不看预设答案；语义审查再核对决定性线索、正确项适配和逐项排除。两轮结论不一致时拒绝该卡。

### 7.5 最终卡片

`final_cards.json` 只由全部 ready 档案确定性渲染，包含：

- 稳定卡片键；
- 显示标题；
- 卡片类型；
- 完整内容；
- 内容哈希；
- 需要解析的根卡引用；
- 对应语义、辨析组或应用审查 ID。

显示标题不是唯一身份来源。标题变化必须通过稳定键和旧 card ID 决定更新或新建，防止因改标题产生重复卡。

### 7.6 发布清单

`release_manifest.json` 是唯一授权对象，至少包含：

```text
schema_version
release_id
source_inventory_hash
semantic_registry_hash
comparison_groups_hash
application_review_hash
final_cards_hash
target_snapshot_hash
deck_id + deck_name
chapter_routes[type -> id + name]
before_count_by_chapter
expected_after_count_by_chapter
action_counts
engine_tree_hash
skill_tree_hash
quality_report_hashes
release_hash
```

`release_hash` 对除自身外的完整规范化清单计算。内容、动作、卡组、章节、类型映射、数量、代码树或审查报告任一变化都会生成不同哈希。

Git 提交 SHA 不写进同一提交中的发布清单，避免“提交内容包含自身提交号”的循环依赖。GitHub 工作流在清单外部把 `release_hash`、合并后的精确 `main` 提交 SHA和部署记录绑定；清单内部使用发布引擎与 Skill 的树哈希锁定实际执行代码。

## 8. 状态机

发布只能沿以下状态前进：

```text
draft
  -> source_audited
  -> semantic_reviewed
  -> groups_reviewed
  -> applications_reviewed
  -> cards_frozen
  -> plan_frozen
  -> ci_verified
  -> awaiting_user_authorization
  -> authorized
  -> writing
  -> readback_verified
  -> complete
```

规则：

- 任一工件变化都退回 `draft` 并产生新 `release_hash`；
- `authorized` 只由 GitHub 受保护环境产生；
- `writing` 后发现内容错误不得在线修补，必须停止并创建新发布；
- 写入中断可以使用同一不可变发布包恢复，但不得改变计划；
- 线上状态与冻结快照不一致时，发布转为 `stale` 并失效；
- `complete` 必须有线上完整回读报告。

## 9. 质量审查分层

### 9.1 确定性机器门禁

检查：

- 来源覆盖状态完整；
- 稳定键、词面、义项和标题唯一；
- 证据位置存在且来源类型合法；
- ready 记录字段完整；
- 禁止模糊指代和已知套话；
- 近义组结构、顺序、成员上限和重叠说明；
- 应用价值决定无缺失、无重复；
- 卡片引用、语法版本和内容哈希；
- 动作数量方程；
- 每章类型与数量；
- 当前快照、发布清单和代码提交哈希；
- GitHub 最终授权状态。

### 9.2 全量语义审查

对每条记录回答：

- 词义是否准确、清晰、可背诵；
- 特别之处是否增加了与近义词不同的信息；
- 判断维度是否真的能帮助做题；
- 易错边界是否具体而非通用提醒；
- 近义组是否具有共同语义基础；
- 最小差别是否形成真正对照；
- 应用题是否存在唯一答案；
- 每个错误选项是否因明确语义条件被排除。

机器相似度只负责发现疑点，不能自动宣布语义正确。高相似内容必须有逐项审查结论和具体理由。

### 9.3 独立性要求

生成与验收不得使用同一个未经隔离的判断结果。复杂语义和应用题需要独立审查回合；审查者读取原始证据和最终候选，不读取生成者的自我辩解。独立审查仍无法确定时标为证据不足，而不是补全字段。

## 10. GitHub 保护与最终授权

### 10.1 内容 PR 阶段

内容 PR 不获得墨墨令牌。必须通过：

- 全部单元和集成测试；
- 来源覆盖门禁；
- 语义和辨析结构门禁；
- 应用卡质量门禁；
- 发布清单完整性和哈希门禁；
- Skill 安装一致性测试；
- 工作流静态安全检查。

所有检查通过后可以自动合并到 `main`，不把合并动作作为日常第二次用户授权。

### 10.2 安全关键文件

以下文件不得由普通内容 PR 同时修改：

- `.github/workflows/maimemo-release.yml`；
- 令牌访问和写入客户端；
- 发布清单验证器；
- GitHub 授权验证器；
- CODEOWNERS 和分支保护配置。

修改这些文件时必须建立独立安全 PR并由用户审阅。常规内容发布不得包含安全关键代码变化。

### 10.3 最终授权阶段

合并后的受信任 `main` 工作流由 Codex 发起，输入精确的 `release_hash` 和提交 SHA。工作流分成两个作业：不绑定环境、无令牌的 `prepare-release`，以及依赖前者并绑定受保护环境的 `write-release`。

`prepare-release` 在完全没有墨墨令牌的条件下完成：

1. 确认运行代码来自 `main` 的精确提交；
2. 重算发布清单哈希；
3. 确认清单中的引擎树哈希、Skill 树哈希与当前提交一致；
4. 确认所有必需检查对同一提交成功；
5. 展示卡组、三章节、动作数量和发布哈希摘要；
6. 将精确发布摘要写入 GitHub 作业摘要，并把受保护环境的审阅链接指向该摘要。

随后 `write-release` 进入 `maimemo-final-release` 受保护环境等待用户批准。环境仅允许 `main` 分支部署，不允许 `refs/pull/*/merge`。用户批准该部署后，环境才向 `write-release` 释放 `MAIMEMO_TOKEN`。

如果批准被拒绝、取消、超时或 GitHub 检查失败，作业无法获得令牌并结束。不得存在本地备用写入路径。

## 11. 写入协议

### 11.1 写入前

获得环境授权后仍先执行只读检查：

- 卡组和三个章节的 ID、名称均与发布清单一致；
- 线上当前数量和内容哈希与目标快照一致；
- 新章节必须为空，或只包含本发布已经成功写入且内容完全一致的卡；
- 不存在无法解析标题、重复稳定键或同名异内容卡；
- 没有另一发布占用同一牌组并发锁。

任何不一致都在第一次写请求前失败。因为发布目标已变化，后续必须生成新发布并重新授权。

### 11.2 顺序

1. 写入或更新近义辨析卡；
2. 回读并验证唯一真实 `mkjr_` 根 ID；
3. 解析基础词义卡中的根引用；
4. 写入或更新基础词义卡；
5. 写入或更新场景应用卡；
6. 全量回读三个章节。

### 11.3 幂等和恢复

- 每次动作前按稳定键读取线上状态；
- 同名同内容视为已完成并跳过；
- 同名不同内容立即阻断；
- 更新动作必须同时匹配旧 card ID和冻结前内容哈希；
- POST 发生超时或连接断开时不得盲目重试，先回读确认服务器是否已处理；
- 每个成功动作写入发布日志，记录动作、card ID、root ID、内容哈希和时间；
- 作业重启时以线上状态为事实来源，日志仅用于诊断；
- API 限流使用服务端提示和有上限退避，不依赖固定等待值；
- 同一牌组同一时间只允许一个发布工作流。

### 11.4 停止规则

遇到以下任一情况立即停止：

- 线上快照漂移；
- 标题、稳定键、card ID或root ID冲突；
- 章节类型错误；
- API返回不明确且回读不能确认结果；
- 连续限流或服务异常超过策略上限；
- GitHub 作业取消；
- 用户撤销环境授权。

停止后不得报告完成，必须产出可恢复状态和精确未完成动作清单。

## 12. 写后验收

完整回读必须验证：

- 每个章节的实际数量等于发布清单；
- 每章只包含规定类型；
- 计划标题、稳定键和内容逐张一致；
- grammar version 全部为3；
- 根卡引用全部存在且指向正确辨析卡；
- 未解析占位符为0；
- 重复标题、重复基础词义和计划外新增为0；
- create、update、unchanged 和跳过数量与发布日志一致。

只有上述结果全部通过，GitHub 检查才标记为成功并生成 `readback_report.json`。成功的回读报告必须绑定同一个 `release_hash` 和 GitHub 作业 ID。

## 13. 隐私与公开仓库

代码、Skill 和通用测试可以公开。新材料默认标记为 `local_only`，不得因为仓库公开而自动上传：

- 完整课程转写；
- 用户未批准公开的学习材料；
- API令牌或其他凭据；
- 带有本机绝对路径的工件。

需要进入公开 PR 的派生内容必须先产生隐私清单，明确哪些内容会公开。来源证据优先保存稳定来源 ID、位置和必要短摘录，不上传完整课程文本。若某次发布依赖不能公开的材料，公开 CI只验证发布工件的结构和哈希，语义证据保留本地；报告必须明确这不是外部独立语义证明。

## 14. 测试策略

### 14.1 Skill 基线测试

编辑 Skill 前，使用历史失败场景运行无新 Skill 的基线测试，记录代理是否会：

- 命中标题后直接跳过旧卡；
- 只复用旧辨析 root ID；
- 把课程大组直接当近义组；
- 字段填满后忽略学习价值；
- 在应用卡缺失时仍宣布完成；
- 用户改章节后沿用旧授权；
- GitHub 最终检查失败后继续本地写入；
- 网络中断后盲目重试 create；
- 把程序结束误报为任务完成。

更新 Skill 后用相同场景复测，确保行为发生可观察变化。

### 14.2 代码测试

至少覆盖：

- 发布清单规范化和哈希稳定性；
- 任一字段变化使授权失效；
- 三章节路由交换被拒绝；
- 章节名称相同但 ID错误被拒绝；
- 快照漂移在首次写入前被拒绝；
- 同名同内容安全恢复；
- 同名不同内容阻断；
- POST成功但响应丢失后的回读恢复；
- 根卡创建、回读、基础卡引用顺序；
- 429和临时网络错误策略；
- 并发发布锁；
- GitHub检查失败、错误提交或错误发布哈希时无法进入写入；
- 每章数量正确但卡片类型互换时回读失败；
- 不可解析线上卡阻断；
- 令牌不出现在异常、日志、工件和测试快照中。

### 14.3 变异测试

自动对合格发布包实施恶意修改：

- 改动一个字；
- 删除一条应用价值决定；
- 复制一张基础卡；
- 用释义改写特别之处；
- 复制定义作为最小差别；
- 调换两个章节 ID；
- 修改预计数量；
- 使用旧快照；
- 替换引擎或 Skill 树哈希；
- 伪造本地批准 JSON。

每种修改都必须至少触发一个明确门禁。

### 14.4 影子发布

正式接触墨墨前，在假 API和当前冻结的869张成果上执行完整影子发布：

- 不提供真实令牌；
- 模拟中断、限流、重复和快照漂移；
- 验证恢复结果不重复；
- 验证三章节完整回读；
- 验证没有 GitHub 授权时无法调用写传输层。

## 15. 一次授权的用户体验

正常任务不让用户参与中间批次审查。系统在内部完成提取、生成、全量审查、返修和 CI。只有进入 `awaiting_user_authorization` 后，向用户展示一次：

- 来源范围与覆盖率；
- 基础、辨析和应用卡数量；
- create、update、unchanged、manual-review 数量；
- 三章节路由和写前写后数量；
- 证据不足或冲突数量；
- 公开数据范围；
- 精确 `release_hash`。

用户批准一次后执行发布。若内容或目标发生变化，原批准作废；这不是重复询问，而是新的发布对象。基础设施失败后的安全恢复优先在同一受保护作业内完成；若 GitHub 要求重新批准新的部署运行，必须再次显示同一个发布哈希，不能悄悄绕过。

## 16. 迁移顺序

1. 把当前个人 Skill 导入仓库作为主版本；
2. 为历史失败场景建立无新 Skill 的基线测试；
3. 建立发布清单 v2及哈希测试；
4. 建立三章节路由、线上漂移和写入恢复测试；
5. 审计当前公开仓库中的来源摘录和派生内容，确认继续公开或移除敏感材料；
6. 建立受保护 GitHub 发布工作流；
7. 修正 `maimemo-final-release` 仅允许 `main` 部署；
8. 配置安全关键文件保护；
9. 将墨墨令牌轮换后保存为环境 secret；
10. 删除本地令牌依赖和本地写入入口；
11. 运行 Skill 前后对照测试、变异测试和影子发布；
12. 由用户审阅安全摘要；
13. 才允许新材料使用该 Skill 进入第一次真实发布。

## 17. 完成标准

只有同时满足以下条件，Skill 升级才算完成：

- Skill 主版本和安装版本哈希一致；
- 历史失败场景的基线失败和升级后通过均有记录；
- 所有单元、集成、变异和影子发布测试通过；
- GitHub 分支、环境和安全关键文件保护已实际验证；
- GitHub 最终授权失败时，写入传输层拿不到令牌；
- 本地工作区、Skill 和日志中不存在墨墨令牌；
- 三章节路由和数量属于发布哈希；
- 写入中断可恢复且不产生重复；
- 线上回读失败时不会报告完成；
- 用户只需对最终不可变发布对象授权一次。
